# 自主唤醒交互系统 · 原理说明

> 用途：说明"默自己醒过来"这套机制是怎么跑的，以及**想改某个数值该去哪一行**。
> 维护：机制改动后同步更新这里。
> 最后更新：2026-10-04

---

## 一、这套系统在干什么

雪不找默的时候，**默也会自己醒过来**，醒来后他有几点"体力"，可以做几件事：
跟你说句话、在小屋里逛逛、调整自己的心情、或者什么都不做。

触发方式：**外部定时器每 10 分钟敲一次门**（配置在外站，仓库里没有），
但**不是每次敲门都会唤醒**——要过两道门。

---

## 二、两道门（最重要的一节）

```
外部定时器（每 10 分钟）
      ↓
【第一道门】深夜保护 —— 静默时段内直接挡回
      ↓
【第二道门】随机冷静期 —— 没等够就挡回
      ↓
✅ 真正的一次唤醒（消耗体力、执行动作、写唤醒日志、重设冷静期）
```

### 第一道门：QUIET_HOURS（深夜保护）

```js
// server.js 约 110 行
const QUIET_HOURS = { start: 0, end: 7 };
```

含义：**0 点到 7 点之间不唤醒**，也就是允许窗口是 **07:00–24:00**。

用在两处（**改的时候两处一起生效**，因为是同一个常量）：
- `shouldPush()` —— 10 分钟敲门时判断
- 唤醒端点内部 —— 硬校验

> 📌 **历史**：原来是 `{ start: 2, end: 12 }`，即允许窗口 **12:00–02:00**。
> 2026-10-04 雪要求改成 07:00–24:00，好让默能看见清晨的景色。

### 第二道门：随机冷静期

```js
// server.js 约 23-24 行
const COOLDOWN_MIN_MINUTES = 260;
const COOLDOWN_MAX_MINUTES = 330;
```

每次唤醒**结束后**，在 260–330 分钟之间随机取一个值，存进 `push_state.cooldown_minutes`；
下次敲门时若没等够就挡回。

**为什么是这两个数**：一天 4 次唤醒之间有 3 段冷静期。

| 参数 | 3 段合计 | 早上 7 点起算，第 4 次落在 |
|---|---|---|
| 原 120–210 | 6–10.5 小时 | 13:00–17:30（傍晚就醒完，太早） |
| 现 260–330 | 13–16.5 小时 | 21:30–23:30（平均 ≈22:30） |

> ⚠️ `cooldown_minutes` 存在数据库里，所以**改常量只影响下一次唤醒之后**的取值。

### 每日上限

```js
// server.js 约 22 行
const PUSH_DAILY_LIMIT = 4;
```

一天最多唤醒 4 次。次数是**算出来的**（`getTodayActionLog(日期).length`），不是单独存的计数器。

> ⚠️ **"今天"的边界用服务器本地时区**（`getDateStr()` 就是纯日历日期）。
> Render 跑在 UTC，所以目前的边界实际是 **北京时间早上 8 点**——这是时区副作用，不是有意设计。
> 若哪天要精确控制边界，得单独写一个"北京时间 + 指定截断小时"的函数。

## 三、唤醒后默能做什么

```js
// server.js 约 26-27 行
const WAKE_ENERGY_POINTS = 2;   // 每次唤醒的体力
const WAKE_MAX_ACTIONS = 2;     // 体力限制下的最大动作数
```

动作在 `WAKE_MENU` 里定义（菜单式，选项间可以跳转），执行入口是 `executeWakeAction(action)`。

| 动作 type | 做什么 | 体力 |
|---|---|---|
| `send_message` | 给雪发一条消息 | -1 |
| `explore_room` | 在小屋里逛一个角落（见下） | -1 |
| `adjust_mood` | 调整自己的心情值 | -1 |
| `do_nothing` | 什么都不做，安静待着 | 0 |

### 彩蛋：EXPLORE_SPOTS

```js
// server.js 约 3790 行
const EXPLORE_SPOTS = [ { spot: '桌柜', text: '…' }, … ];  // 5 条固定文本
```

`explore_room` 就是从这 5 条里**随机抽一条**返回。

> ⚠️ **它必然会被"探索完"**——不是内容不够，是结构问题：常量数组 + 随机抽，
> 没有状态、没有累积、没有解锁顺序，同一个地方永远同一句话。
> 想耐玩需要三件事：① 探索留下状态 ② 渐进解锁 ③ 默/雪的行为能改变它。

## 四、唤醒日志与记忆的关系

- 每次唤醒都写一条日志（`logWakeAction`），供前端"今日唤醒"和唤醒注入使用
- 日志**会进记忆海**（`source='wake'`），但**被排除在记忆书之外**
  （原因：唤醒流水账会污染记忆书，2026-09-08 已摘除）
- 唤醒时的动作还会触发情绪事件（`recordWakeActionEmotion`）

> 📌 **待办**：雪想给"唤醒日志/小屋生活"做一条**独立召回通道**（和对话记忆分开配比），
> 最小实现是利用 `aevum_memories.source` 字段按来源分通道，不用新建表。

## 五、天气系统

天气同时驱动三处，必须一致：**注入给默的文本 / 小屋窗户的景色 / 后花园的浇水判断**。

### 数据源

| 优先级 | 源 | 说明 |
|---|---|---|
| 1 | **和风天气 QWeather** | 需 `WEATHER_PROVIDER=qweather` + `QWEATHER_KEY` + `QWEATHER_HOST` |
| 2 | Open-Meteo | 免费无需 key，全球模式；**中国夏季局地雷阵雨偏差大** |
| 3 | wttr.in | 最后的兜底 |

和风失败会**自动降级**到 Open-Meteo，不会没天气。

```js
// server.js 约 1577-1578 行
const WEATHER_DEFAULT_CITY = '晋江';
const WEATHER_CACHE_TTL = 30 * 60 * 1000;  // 30 分钟缓存
```

### ⚠️ 和风的两个坑（都实测踩过）

1. **必须用专属 API Host**（形如 `xxx.re.qweatherapi.com`），公共域名已失效
2. **响应是 gzip**，而 **Node 的 fetch 会自动解压、却仍然保留 `content-encoding: gzip` 响应头**。
   照着头去 `gunzipSync` 会抛 `incorrect header check` → 和风路径每次失败、**静默降级**回 Open-Meteo。
   **正确做法：按实际字节的 gzip 魔数判断**，不能按响应头。

### 两层注入（2026-10-04 重写）

原来把"此刻的快照"和"今日概览"揉成一句（`【当前天气】晋江：晴…最高32/最低26`），
傍晚下雨时那句"晴"就显得是假话。现在分成两层：

```
【天气 · 晋江】
预报说今天阴，今天不太会下雨；气温 21~26°C。          ← 今天整体
现在外面多云，24°C（体感 21°C），湿度 57%，风速 30km/h。现在是下午。   ← 此刻
（两者不一致很正常——比如预报有雨但此刻还没下。）
```

- **预报层**：今天整体天气 + 降水时段结论
- **实况层**：此刻天气 / 体感 / 湿度 / 风速
- 降水结论由 `summarizeRainWindow()` 把逐小时 `pop` **压成一句人话**
  （`降水概率较高的时段：15:00 到 19:00（最高 85%，多为中雨）`）——
  **默要的是结论，不是 24 行数据**

### 冬季映射成雪

```js
const WINTER_SNOW_MONTHS = [11, 0, 1];  // 12月/1月/2月（getMonth 从 0 起）
```

晋江一年到头难见雪，但小屋想有。规则：**冬季 + 实况是"雨/阴"或正在降水 → 展示成"雪"**。
只在**展示层**映射，机制（浇水判断等）不变。

## 六、后花园（建设中）

### 设计原则

- 时间按**自然日**结算，**不设定时任务**；每次唤醒用"当前自然日 − 上次结算日"推进
- **一天可能唤醒多次，只有跨天那天推进**（同一天多次唤醒只结算一次）
- **不注入花园状态给默**——注入的是"背包里有什么 + 金币 + 之前唤醒做过什么"，
  让他自己走过去看，保留惊喜（比如去鸡棚才发现下蛋了）
- **文案不写死在代码里**：全部在 `garden-text.json`，存 Supabase `garden_text(id=1)` 时优先读库

### 查看时的三个维度

| 维度 | 内容 |
|---|---|
| ① 生长阶段 | 每种作物自己的 2~4 段描写（花第 3 段是花苞，菜是"结果/鼓起来"） |
| ② 浇水状态 | 天晴：没浇 / 浇过一次（1/2）/ 够了（2/2）；**下雨天有专门一句**——按雨量分小雨/大雨 |
| ③ 意外事件 | 生虫（叶子被啃掉一小块）、杂草、鸟啄、风、瓢虫 |

### 生长阶段的天数映射（写文案不用管代码）

- 第 0 天 = 第 1 段；成熟日 = 最后一段
- **中间只有 1 天 → 3 段（跳过花苞）**：雏菊、小白菜（2 天成熟）
- 中间 ≥2 天 → 4 段：其余全部

### 意外事件与代价

| 事件 | 代价 |
|---|---|
| **生虫** | **-1 体力**除虫；**连续两天没除 → 枯萎** |
| **杂草** | **-1 体力**拔草 |
| 鸟啄 / 风 / 瓢虫 | 纯描述 |

生虫概率：**每天初次唤醒时每块田独立 10%**。

### 经济

- 初始：4 块田、5 颗种子（雏菊×2、小白菜×2、胡萝卜×1）、30 金币
- 小鸡 200 金币/只（上限 3 只），长大后每天第一次唤醒每只 30% 生蛋（前一天喂过 → 35~40%）
- 商店做成**无人机配送**：默下单 → **下一次唤醒时到货**（下单即扣钱）

### 代码结构（与射精值系统同套路）

| 文件 | 作用 |
|---|---|
| `garden-core.js` | **纯函数状态机**（无 IO、确定性、可单测） |
| `scripts/test-garden.js` | 单测 |
| `garden-text.json` | 全部文案 + 可调数值（种子价/售价/成熟天数/保质期/每日浇水次数） |
| `setup_garden_state.sql` | 状态表（状态存 Supabase，与 `arousal_state` 同套路） |

## 七、小屋家具（规划中）

**花束、窗户、壁炉、水晶球本质是同一个东西**——一份"小屋里摆了什么"的清单。
建议统一成一份 `cabin_decor`，这样加新家具只是往清单里加一行，不用写三套逻辑。

| 家具 | 交互 |
|---|---|
| **窗户** | 走到窗边看到窗外景色——**同一份天气数据**，按 6 种天气 × 4 个时段组合 |
| **壁炉** | 走近可**点燃/浇灭**（免费，不花体力）；联动：冬天点着 → 窗玻璃起雾 |
| **水晶球** | 每天限一次、**免体力**；随机抽 78 张塔罗之一 + 正逆位随机；抽完默写几句（进记忆） |

> 水晶球的意义：它是**解释型**内容——78 张 × 正逆位，但**不需要写 156 段文案**，
> 只需"牌名 + 一句意象"，其余让默自己解读。**这是唯一能真正解决"彩蛋会被探索完"的路子**：
> 内容由模型生成，而不是从常量数组里抽。
> 措辞上往"镜子/映照心境"引，不要写成"今天注定如何"（和人设的诚实、不迷信冲突）。

## 九、踩过的坑（都别再踩）

1. **搜关键词别下结论**：找唤醒窗口时我只搜了 `getHours`，漏了 `getTimeInfo().hour`，
   就断言"代码里没有窗口"——**实际有**。找不到 ≠ 不存在，先换关键词。
2. **和风的 gzip**：Node fetch 已自动解压但头还在，按头判断会二次解压报错并**静默降级**。
3. **分页必须显式 order**：`range()` 不写 `order` 时顺序不确定，边更新边翻页会漏行/重复行。
4. **时区**：`getDateStr()` 用服务器本地时区（Render = UTC），"今天"的边界实际是北京时间 8 点。
5. **文案别写死**：`EXPLORE_SPOTS` 的教训——写死在常量数组里，抽完就没了，改一句还得动代码。

- 田块叫法随场地：`1 号田` / `花田 1 号` / `菌床 2 号`
- **老存档迁移**：没有 site 的归菜田、缺的场地自动补齐、已种的东西和长势不丢（有单测）

- 服务端接口在 `server.js`，需要 Render 上的 `DEBUG_TOKEN`；**没配就一律 404**

- ⚠️ **关闭方式**：点页面上的「关闭沙盒」，或者**等一次部署**（重启会清空内存）
- **闲置 30 分钟自动关** —— 所以最坏也只是"默晚半小时醒"，不会一直不醒
- 需要参数的选项必须写进页面的 `NEEDS`，否则点进去没有输入框（**这个坑踩了三次**）

**它的价值**：纯内核单测照不到"接口层"——工具参数缺了、中文名传不进去、状态没同步，这些**只有在沙盒里以默的视角点一遍才会露出来**。今天靠它抓出十几个。

## 十三、新踩的坑（接第九节）

6. **别拿"符号出现次数"当核对手段**：`siteOfNode` 出现 2 处看着正常，实际是「定义 + 一处使用」凑够了数，**动作那五处根本没接上**。次数对 ≠ 接对了。
7. **全局替换会误伤入口**：为让花园动作留在原地，把 `nextNode: 'garden'` 全改成 `ctx.node`，结果 `case 'garden'`（走进后花园的入口）也变成了原地不动 —— **后花园进不去了**。
8. **PowerShell 引号**（今天踩了七八次）：双引号里 JS 模板字面量的 `${...}` 会被 PS 抢先解释（导致替换静默失败）；PS 里 `$1` 是它自己的变量、不是正则反向引用；`\"` 不是转义；单引号串里不能再嵌单引号（提交信息一长就中）。
9. **往数组/对象里插一项，先看它前面那一项的逗号**（今天四次语法错都是这个）。
10. **加了内容要改依赖数量的断言**（商品数从 34 到 35 就挂了一条测试）。
11. **改了 server.js 必须真启动一次**：`node --check` 加单测全过，路由注册失败照样让服务起不来（线上 status 1 那次）。Express 5 **不允许裸 `*` 路径**。
